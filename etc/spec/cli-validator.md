# Main Spec: CLI-валидатор базы знаний (Этап 1)

## Purpose
Обеспечить валидацию структуры OKF-бандла и YAML-метаданных (frontmatter) для поддержания базы знаний в актуальном состоянии. 
*Примечание: На этапе 1 (MVP) мы валидируем только сами файлы знаний. Проверка роутера `AGENTS.md`, интеграция с Git и CI/CD вынесены в Этап 2.*

---

## Requirement: Структура и парсинг YAML
Система ДОЛЖНА проверять наличие и корректность YAML-блока в файлах знаний.

#### Сценарий: Отсутствие YAML-шапки
- **WHEN** файл знаний не начинается с открывающего блока `---`.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

#### Сценарий: Ошибка парсинга
- **WHEN** YAML-блок содержит синтаксические ошибки или является списком/скаляром, а не словарём (mapping).
- **THEN** система возвращает критическую ошибку (Exit code: 1).

---

## Requirement: Служебные файлы
Система ДОЛЖНА проверять структуру служебных файлов в корне бандла.

#### Сценарий: Наличие YAML в служебных файлах
- **WHEN** файлы `index.md` или `log.md` содержат YAML-шапку.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

---

## Requirement: Типизация и базовые поля
Система ДОЛЖНА проверять корректность обязательных полей.

#### Сценарий: Некорректный тип документа
- **WHEN** поле `type` отсутствует, пустое или его значение не входит в утвержденный словарь.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

#### Сценарий: Некорректные теги
- **WHEN** поле `tags` присутствует, но не является списком строк.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

---

## Requirement: Валидация происхождения (Provenance)
Система ДОЛЖНА проверять наличие ссылок на источники для обеспечения трассируемости знаний.

#### Сценарий: Отсутствие источников
- **WHEN** блок `provenance.sources` отсутствует или является пустым списком.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

---

## Requirement: Валидация доверия (Trust & Confidence)
Система ДОЛЖНА проверять поля, отвечающие за уровень доверия к данным и маршрутизацию уведомлений.

#### Сценарий: Некорректный уровень уверенности
- **WHEN** поле `trust.confidence` отсутствует или его значение выходит за пределы `0.0` – `1.0`.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

#### Сценарий: ИИ выдает себя за человека
- **WHEN** `trust.generated` равно `script` или `agent`, а `trust.confidence` равно `1.0`.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

#### Сценарий: Отсутствие ответственного
- **WHEN** поле `trust.verified_by` отсутствует.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

---

## Requirement: Валидация жизненного цикла (Freshness)
Система ДОЛЖНА проверять корректность дат для работы Freshness Engine.

#### Сценарий: Некорректный формат дат
- **WHEN** поля `freshness.last_reviewed` или `freshness.stale_after` отсутствуют или не являются валидными датами.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

#### Сценарий: Документ протух раньше проверки
- **WHEN** дата `freshness.stale_after` меньше, чем дата `freshness.last_reviewed`.
- **THEN** система возвращает критическую ошибку (Exit code: 1).

---

## Requirement: Проверка целостности графа (Гигиена)
Система ДОЛЖНА проверять связи между документами.

#### Сценарий: Битые ссылки (Broken Links)
- **WHEN** в тексте есть markdown-ссылки на несуществующие файлы в бандле.
- **THEN** система выводит предупреждение (Warning, Exit code: 0).

#### Сценарий: Недостижимые файлы (Orphan Concepts)
- **WHEN** на файл концепта нет ни одной ссылки из других файлов.
- **THEN** система выводит предупреждение (Warning, Exit code: 0).

---

## Приложение 1: Эталонный контракт данных (To Be)
Каждый файл знаний ДОЛЖЕН содержать следующую шапку (с примером заполнения):

```yaml
---
type: "Architecture"
tags: [auth, security]
provenance:
  sources: 
    - "git://src/auth.py"
trust:
  generated: "human"            
  verified_by: "teamlead_ivan"  
  confidence: 1.0               
lifecycle:
  status: "stable"              
freshness:
  last_reviewed: "2026-10-19"   
  stale_after: "2027-10-19"     
timestamp: "2026-10-19T10:00:00Z"
---
